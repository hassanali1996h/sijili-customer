# الأمان ومنع التلاعب

## الموافقة ليست الإشعار

إرسال الإشعار لا يثبت موافقة العميل. المطلوب:

1. الطلب ينشأ بحالة `pending`.
2. التطبيق يعرض تفاصيل الطلب بعد تسجيل دخول العميل برقم الهاتف الموثق.
3. لا يتم التأكيد إلا باستدعاء RPC خادمي مصادق عليه.
4. يتحقق الخادم من أن المستخدم هو العميل المرتبط بالعملية وأن حالتها لا تزال `pending`.
5. يسجل القرار والوقت وهوية المستخدم في `transaction_events`.
6. التكرار لا ينفذ القرار مرتين؛ استخدم idempotency key وقيداً فريداً.

## سجل غير قابل للتعديل المباشر

- لا تمنح تطبيقات المستخدم صلاحية INSERT/UPDATE/DELETE مباشرة على `ledger_transactions` أو `transaction_events`.
- أنشئ العمليات عبر RPC محددة بصلاحيات `SECURITY DEFINER` مع `SET search_path` مضبوط والتحقق من `auth.uid()`.
- امنع DELETE على سجل العمليات والأحداث.
- امنع تعديل المبلغ أو النوع أو صاحب العملية أو الارتباط بعد الإنشاء.
- بعد تأكيد العملية، لا تغير حالتها إلى قيمة أخرى. التصحيح يكون بإجراء عكسي جديد يوافق عليه الطرفان.
- احتفظ بنسخة احتياطية دورية واختبر استعادتها.

## Row Level Security

- فعّل RLS على كل جدول يحتوي بيانات مستخدم.
- صاحب المحل يرى سجلات محله وعملاءه فقط.
- العميل يرى سجلات ارتباطاته المقبولة فقط.
- لا توجد سياسة عامة تسمح باستعراض رقم هاتف أو ديون عملاء.
- مفاتيح الخدمة تستخدم في Edge Functions فقط.
- اختبر RLS بحسابين مستقلين على الأقل (محلان مختلفان وعميلان) للتأكد من عدم تسرب البيانات.

## تسجيل الهاتف

- رقم E.164 بعد OTP فقط.
- فرض حدود إرسال OTP، مدة إعادة الإرسال، CAPTCHA/anti-abuse، ومراقبة تكلفة SMS.
- لا تسجل OTP أو رموز الجلسات أو محتوى المعاملات في سجلات التطبيق.
- لا تعتمد على رقم هاتف من إدخال المستخدم قبل تحقق Auth.

## جهاز صاحب المحل

- معرف تثبيت عشوائي ينشأ محلياً ويحفظ عبر SecureStore.
- جهاز نشط واحد للحساب التجاري.
- نقل الجهاز بعد OTP حديث، مع إلغاء الجلسة/الربط السابق. يمنع قيد فريد استخدام نفس هوية تثبيت التطبيق لحساب تاجر آخر في الوقت نفسه.
- لا تجمع IMEI أو serial number أو Advertising ID أو بصمة عتاد. معرّف التثبيت وحده ليس ضماناً ضد إعادة تثبيت التطبيق أو استخدام هاتف آخر؛ أضف Play Integrity / App Attest أو مراجعة دعم عند الحاجة، ولا تعد بمنع إساءة الاستخدام بنسبة 100%.
- عنوان IP قد يستخدمه مزود المصادقة لأغراض الأمن ومكافحة الإساءة، لكنه ليس معرفاً دائماً ولا معياراً لمنح الشهر المجاني.

## حد الدين

يجب تنفيذ فحص السقف داخل قاعدة البيانات في المعاملة نفسها التي تنشئ الطلب، مع `SELECT ... FOR UPDATE` على customer_link أو قفل مناسب. لا يكفي فحص في واجهة التطبيق؛ طلبان متزامنان قد يتجاوزان الحد إن تم الفحص محلياً.

## الاشتراكات

- العميل لا يستطيع كتابة `paid_until` أو حالة الاستحقاق.
- RevenueCat Webhook يتحقق من Authorization header.
- يجب منع تكرار الحدث حسب `event.id`، ثم الاستعلام من RevenueCat عن Subscriber الحالي قبل تحديث قاعدة البيانات.
- لا تحفظ Secret API Key في تطبيق الهاتف.
- دعم استعادة الشراء وتغيير الجهاز من خلال Supabase UUID ثابت كـ RevenueCat App User ID.
- عند انتهاء الاشتراك، يظل وضع القراءة فقط ممكناً حتى لو انقطع الإنترنت عن التطبيق؛ لا تسمح بكاش قديم يمنح كتابة غير مستحقة.

## الخصوصية

- لا تعرض تفاصيل الدين في نص إشعار شاشة القفل؛ استخدم إشعاراً عاماً مثل «لديك طلب حساب جديد، افتح التطبيق للمراجعة».
- لا تستخدم Analytics لتسجيل الاسم أو رقم الهاتف أو المبلغ أو وصف المشتريات.
- شفر الاتصال عبر TLS، واستخدم تخزيناً آمناً للجلسات.
- حدد مع محامٍ فترات الاحتفاظ بالسجلات ومتطلبات حذف الحساب. لا تعد المستخدم بحذف سجلات مالية تخص الطرف الآخر إن كان القانون يوجب الاحتفاظ بها.

## تهديدات واختبارات إلزامية

- عميل يحاول قراءة سجل محل آخر.
- محل يحاول تعديل مبلغ بعد تأكيده.
- محل يرسل طلبين متزامنين يتجاوزان سقف العميل.
- عميل يكرر الموافقة مرتين أو يحاول الموافقة على طلب شخص آخر.
- صاحب محل يحذف التطبيق/يغير الهاتف لإعادة التجربة.
- مزور يستدعي RPC مباشرة دون اشتراك.
- Webhook مكرر أو غير موقع.
- انتهاء الاشتراك مع بقاء البيانات قابلة للقراءة.
