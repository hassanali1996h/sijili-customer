# خطة تنفيذ دفتر الديون

هذه الخطة تحوّل مواصفات المنتج إلى مراحل صغيرة يمكن مراجعتها واختبارها. ستبقى القرارات التجارية المثبتة في `AGENTS.md` و`docs/PRODUCT_SPEC.md` كما هي.

## نتائج فحص حزمة البداية

- الحزمة تحتوي على الهيكل الأولي للتطبيقين، الحزمة المشتركة، ترحيل قاعدة بيانات أولي، ووظيفتي إشعار وWebhook أوليتين. عند الفحص لم يكن فيها `package-lock.json` أو `supabase/config.toml` أو اختبارات قاعدة بيانات؛ أُضيفت هذه الأساسات خلال المرحلة 1.
- Expo SDK 58 هو أحدث إصدار مستقر بحسب سجل Expo بتاريخ 19 نوفمبر 2026. يتطلب Node.js 22.13 أو أحدث، ويستهدف React Native 0.88 وReact 19.3. ملفات البداية تستخدم React 19.2 وبعض إصدارات Expo الأصلية بعلامة `*`؛ يجب محاذاتها مع إصدار SDK الفعلي بواسطة `npx expo install --fix`.
- Node.js 18 الموجود في المسار العام منتهي الدعم ولا يحقق متطلبات SDK. تتوفر نسخة Node.js 24.22.3 داخل بيئة Codex وتفي بالحد الأدنى الموثق، ويمكن استخدامها أثناء التطوير.
- Supabase CLI 3.2.0 مثبت محلياً ومقفل في `package-lock.json`، وأُنشئ `supabase/config.toml`. Docker Desktop وPodman غير مثبتين؛ يلزم أحدهما لتشغيل Supabase محلياً على Windows كي نطبق الترحيل ونشغل pgTAP.
- ترحيل قاعدة البيانات الأولي كبير ولم يُشغّل بعد. أُضيفت ترحيلات لمعالجة إعادة استخدام مفاتيح idempotency بمحتوى/قرار مختلف، وقفل مطالبات Outbox، لكنها غير متحققة على Postgres. ما زالت صلاحيات دوال `SECURITY DEFINER`، عزل الدعوات، وسلوك Outbox بحاجة إلى تدقيق واختبارات RLS فعلية.
- لا توجد بيانات Supabase أو مفاتيح SMS أو RevenueCat أو المتاجر. لا نحتاج أسراراً للمرحلة الأولى، ولا يجوز وضعها في المستودع.
- الفجوات الوظيفية والقانونية والتجارية المعروفة مفصلة في `docs/KNOWN_GAPS.md` و`docs/LEGAL_REVIEW.md` و`docs/STORE_SETUP.md` و`docs/RELEASE_CHECKLIST.md`.

## سجل تنفيذ المرحلة 1

- أُعدّت npm workspaces وقُفلت الاعتماديات. المجموعة الحالية: Expo 58.0.26 المستقر، React Native 0.88.1، React وReact DOM 19.3.0 موحدان في التطبيقين، Expo Router 58.0.32، React Native Web 0.21.4، TypeScript 6.0.3، وSupabase CLI 3.2.0.
- شُغّل `npx expo install --fix` للتطبيقين وأضيفت حزم الويب المتوافقة مع SDK، ثم نجح `npx expo install --check` للتطبيقين ونجح Expo Doctor بنتيجة 20/20.
- نجح `npm run typecheck` للتطبيقين بعد حذف إعداد `baseUrl` المتقادم في TypeScript 6.
- أُضيف اختبار pgTAP أساسي لعزل محلين وعميلين وصلاحيات سجل العمليات.
- تعذر تشغيل `supabase start` برسالة أن Docker وPodman غير موجودين. لذلك لم تُشغّل الترحيلات ولم تُنفذ اختبارات pgTAP؛ المرحلة 1 مفتوحة حتى تتوفر بيئة حاويات ثم تنجح `npm run db:reset` و`npm run db:test`.
- أظهر `npm audit` ثلاث نتائج متوسطة تمر عبر `@expo/fingerprint` و`minimatch`. الإصلاح الآمن داخل نطاق SDK الحالي غير متاح؛ `npm audit fix` يقترح فقط خفض Expo إلى SDK 52، لذلك لم يُطبّق خفض يكسر SDK 58. يعاد فحصها عند صدور تحديث متوافق من Expo.

## سجل مواصلة الواجهات

- بتاريخ 19 نوفمبر 2026 طلب المستخدم مواصلة بناء التطبيقين دون تنزيل Docker الآن. بقيت ترحيلات قاعدة البيانات واختبارات pgTAP معلّقة، واستمر العمل في الشاشات التي تستخدم الـ RPCs الموجودة في الترحيل الأولي.
- أُضيفت لوحة تاجر، إنشاء محل، إضافة عميل بسقف IQD، وإنشاء طلب دين/تسديد ينتظر قرار العميل. تعرض اللوحة حالة الفترة المجانية/القراءة فقط، وتعرض الأرصدة عبر `get_customer_balance`.
- أُضيف دليل عملاء قابل للبحث والصفحات، وصفحة تفصيل العميل للتاجر لتعديل السقف وعرض الرصيد المؤكد والمعلق وإنشاء عملية للعميل المحدد وتصفح السجل.
- أُعيد تصميم واجهة العميل لتعرض الدعوات والطلبات المعلقة والموافقة/الاعتراض. أُضيفت صفحة كشف حساب لكل محل مع رصيد مؤكد/معلق، حد ائتماني، مشاركة نصية للقراءة فقط، وتصفح سجل العمليات على دفعات.
- أُضيف `decline_customer_link` في ترحيل مستقل حتى يستطيع العميل رفض دعوة المحل بأمان ومن دون كتابة مباشرة على الجدول.
- أُضيف ترحيل لإعادة محاولة آمنة: مفتاح إنشاء الطلب لا يعيد سجلًا إذا تغيّرت بيانات الطلب، ومفتاح قرار العميل لا يمكن إعادة استخدامه لتبديل الموافقة إلى اعتراض. الاختبارات على Postgres ما زالت معلّقة.
- رُبط قيد جهاز التاجر بمعرّف تثبيت عشوائي محفوظ في SecureStore، مع طلب OTP حديث عند محاولة النقل من جلسة قديمة. فحص الجهاز على الويب متجاوز للتطوير فقط؛ يلزم اختبار القيد على Android وiOS بعد تشغيل قاعدة البيانات.
- أُضيف حفظ اختيار العربية/السورانية، وفحص لغة الجهاز عبر `Intl`; لم تُضف `expo-localization` بعد، ويجب التحقق من اكتشاف `ckb` على أجهزة Android وiOS قبل اعتماد هذا الجزء.
- أُضيف تسجيل رموز Expo Push اختيارياً في التطبيقين، مع طلب الإذن عند ضغط المستخدم، قناة Android، ورسالة تشرح غياب إعداد EAS. يعالج عامل الإشعارات Outbox بمطالبات ذرية ومدة حجز، إعادة محاولة متدرجة، وحالة dead-letter بعد ثماني محاولات؛ يفحص Expo tickets ويحذف رموز `DeviceNotRegistered`، وتبقى رسائل شاشة القفل عامة بلا مبلغ أو وصف.
- ثُبت `expo-notifications ~58.1.9`، وهو الإصدار الذي توصي به وثائق Expo الحالية لـ SDK 58. فشلت محاولة إعادة `expo install --check` بعد إضافتهما لأن الأمر حاول الاتصال بالشبكة وانتهى بـ `EACCES`؛ فحص TypeScript المحلي نجح.
- أُضيف فتح التطبيق على الصفحة الرئيسية عند الضغط على إشعار. يحفظ العامل تذاكر Expo ويتابع نتائج تمريرها إلى Apple أو Google، ويؤجل فحص النتائج الغائبة حتى 24 ساعة. ينتظر الترحيل اختبار Postgres، وتنتظر عملية النشر إعداد EAS واعتمادات الإشعارات وجدولة العامل.
- أُضيفت مشاركة دعوة من شاشة إنشاء العميل ومن تفاصيل الدعوة، برابط عميق إلى تطبيق العميل. بعد التحقق من رقم الهاتف، يربط المشغل الموجود في قاعدة البيانات الدعوة تلقائياً بهذا الحساب وتظل بحالة انتظار موافقة العميل؛ شاشة الرابط تساعد على تسجيل الخروج إذا كان المستخدم في حساب هاتف آخر.
- أُضيفت المرحلة الأولى من اشتراك التاجر فقط: RevenueCat React Native SDK `11.0.4` (على CocoaPods المستقر لـ Expo؛ SDK 12 يتطلب SPM وما زال دعمه تجريبياً)، وExpo Development Client، وشاشة تعرض أسعار المتجر الفعلية مع الشراء والاستعادة وإدارة الاشتراك. عميل الموبايل يرسل UUID حساب Supabase كـ App User ID.
- أُضيف `revenuecat-sync` محمي بجلسة Supabase، ويستعلم عن الحالة الحالية من RevenueCat بمفتاح الخادم ثم يحدّث صلاحية المحل؛ لا يمنح العميل صلاحية من نتيجة محلية. أُعيد استخدام محلل الاستحقاق نفسه في Webhook.
- لم تُنشأ منتجات المتاجر أو Offering/`merchant_pro` في لوحة RevenueCat، ولم تُضف مفاتيح Public/Secret أو إعداد Sandbox، لذلك شاشة الشراء تعرض حالة الإعداد حتى تُجهز تلك الحسابات. لم تُختبر Edge Functions على Supabase.
- فحص TypeScript نجح للتطبيقين بعد هذه التغييرات. لم يُشغّل Supabase، لذلك لا تعتبر معاملات قاعدة البيانات أو سياسات RLS أو ترحيل رفض الدعوة معتمدة حتى يجري `db:reset` و`db:test`.

## المراحل

- أُضيف ترحيل يربط الدعوات بعد تأكيد الهاتف وتوحيد صيغته، مع استرجاع مسار الدعوة بعد OTP وترجمات العربية والسورانية. أُضيفت شاشتَا إعدادات بطلب حذف محفوظ في Supabase. أُضيفت حالات pgTAP لقبول الربط بعد التأكيد فقط، وعزل طلبات الحذف وعدم تكرارها. تنفيذ الحذف ورابطه العام ما زالا مطلوبين قبل الإطلاق.

### المرحلة 1 — أساس المشروع وقاعدة بيانات محلية

**الملفات:** `package.json`، `package-lock.json`، ملفات `apps/*/package.json` و`tsconfig.json`، `.nvmrc` أو ما يعادله، `supabase/config.toml`، `supabase/migrations/*`، `supabase/tests/*`، و`docs/IMPLEMENTATION_PLAN.md`.

**العمل:** تثبيت إصدارات Expo وReact Native وReact المتوافقة مع أحدث SDK مستقر، ضبط npm workspaces وTypeScript، تثبيت Supabase CLI محلياً بإصدار مقفول، إعداد Supabase المحلي، تشغيل الترحيلات على قاعدة نظيفة، إصلاح أخطاء التهيئة/SQL، وإضافة اختبارات pgTAP أساسية للمخطط وRLS والصلاحيات المباشرة.

**الاعتماديات:** Node.js 22.13+؛ يوصى بنسخة LTS متوافقة. Supabase CLI وDocker Desktop أو بديل Docker-compatible على Windows. لا يلزم حساب مستضاف أو أي سر إنتاجي.

**معايير القبول:** `npm ci` ينجح؛ `npx expo install --check` و`npx expo-doctor` لا يظهران تعارضات غير مبررة؛ `npm run typecheck` ينجح؛ `npx supabase db reset` يطبق كل الترحيلات من الصفر؛ `npx supabase test db` ينجح لاختبارات pgTAP، بما فيها تشغيل الاستعلامات بدور `authenticated` والتحقق من منع الكتابة المباشرة على سجل العمليات. تسجل الملفات التي تغيرت وأي حدود بيئية.

### المرحلة 2 — تثبيت قواعد المحاسبة والأمان في الخادم

**الملفات:** ترحيلات `supabase/migrations/*` واختبارات `supabase/tests/*`، مع تحديث `docs/SECURITY.md` عند الحاجة.

**العمل:** إكمال RLS والصلاحيات على كل جدول، تقوية دوال RPC وسجل الأحداث، معالجة تكرار الطلبات والقرارات، التحقق من سقف الدين داخل معاملة ذرية، تثبيت عدم سلبية الرصيد، وإغلاق حدود الدعوة والربط والحذف.

**الاعتماديات:** المرحلة 1 ناجحة.

**معايير القبول:** اختبارات pgTAP لحسابين ومحلات وعملاء متقاطعين؛ رفض قراءة بيانات الغير والكتابة المباشرة؛ طلبان متزامنان لا يتجاوزان السقف؛ موافقة/اعتراض مكرر لا ينشئ أثراً مزدوجاً؛ لا تعديل أو حذف للعملية المؤكدة؛ صلاحية الكتابة بعد التجربة/الاشتراك يقررها الخادم.

### المرحلة 3 — الهاتف والهوية والجهاز

**الملفات:** التطبيقان في `apps/*/app` و`apps/*/src`، إعدادات Supabase Auth، وRPC تسجيل الجهاز.

**العمل:** دخول OTP برقم E.164، إعداد الملف، حفظ الجلسة بأمان، ربط جهاز التاجر الواحد، وتدفق OTP حديث لنقل الجهاز.

**الاعتماديات:** المرحلة 2؛ اختيار مزود SMS واختبار إعدادات التطوير.

**معايير القبول:** اختبار OTP محلي/تطويري، تكرار الرمز لا ينشئ حساباً مكرراً، العميل غير مقيد بجهاز واحد، نقل جهاز التاجر يتطلب OTP حديثاً ولا يعيد التجربة.

### المرحلة 4 — الأساس المشترك للغة والواجهة

**الملفات:** `packages/shared/src/*` وملفات تخطيط التطبيقين.

**العمل:** إكمال العربية والسورانية، اختيار اللغة وحفظها، RTL واتجاه النص، تنسيق IQD والتواريخ في `Asia/Baghdad`، والتحقق من النصوص وإمكانية الوصول.

**الاعتماديات:** المرحلة 3.

**معايير القبول:** كل النصوص المرئية مترجمة؛ اختبار أسماء عربية/كردية طويلة؛ لا قص أو انعكاس خاطئ في RTL؛ لا عمليات حساب أموال عائمة.

### المرحلة 5 — تدفقات صاحب المحل

**الملفات:** `apps/merchant/app/*` و`apps/merchant/src/*` و`packages/shared/src/*`.

**العمل:** إنشاء ملف المحل، العملاء والدعوات، حد الائتمان، طلبات الدين والتسديد، حالة العمليات وكشوف الحساب، وضع القراءة فقط، وإدارة الاشتراك.

**الاعتماديات:** المراحل 2–4.

**معايير القبول:** لا كتابة بعد انتهاء التجربة/الاشتراك؛ الأرصدة والطلبات المعلقة واضحة؛ جميع التغييرات المالية مصدرها RPC؛ لا تتجاوز حدود الدين في الواجهة أو الخادم.

### المرحلة 6 — تدفقات العميل

**الملفات:** `apps/customer/app/*` و`apps/customer/src/*` و`packages/shared/src/*`.

**العمل:** الدعوات، هوية المحل، الطلبات، التفاصيل والموافقة/الاعتراض، سجل كل محل، كشف قراءة فقط وإعدادات اللغة والحساب.

**الاعتماديات:** المراحل 2–4.

**معايير القبول:** العميل يرى حساباته المرتبطة فقط؛ لا يغير مبلغاً؛ التأكيد/الاعتراض يسجل هوية المستخدم والوقت؛ التطبيق مجاني ولا يحتوي شاشة شراء.

### المرحلة 7 — Outbox والإشعارات والدعوات

**الملفات:** `supabase/functions/notify-event/*`، ترحيلات Outbox واختباراتها، وتسجيل Push في التطبيقين.

**العمل:** قفل ذري يمنع عاملين من أخذ الصف نفسه أثناء مدة الحجز، إعادة محاولة متدرجة، فحص Expo tickets وإزالة الرموز التي يعلن عنها Expo كغير صالحة، ثم إضافة متابعة Expo receipts غير المتزامنة. إعدادات الجدولة وEAS جزء من ربط النشر. رسائل شاشة القفل عامة ولا تكشف تفاصيل مالية؛ الدعوات الخارجية لا تتضمن مبلغاً أو وصف دين.

**الاعتماديات:** المراحل 2 و5 و6؛ مفاتيح Expo/SMS توضع كأسرار خادم عند الربط.

**معايير القبول:** لا يعالج عاملان الصف نفسه في الوقت ذاته ما دامت مطالبته فعالة؛ يسجل العامل النتيجة ويعيد المحاولة أو يحولها إلى dead-letter، وتُعالج Expo receipts عند إعدادها؛ الضغط على الإشعار يفتح التطبيق؛ الإشعار لا يثبت الموافقة؛ لا يظهر مبلغ أو وصف في Push أو SMS. التسليم الخارجي at-least-once وقد يتكرر عند انتهاء مهلة غير محسومة.

### المرحلة 8 — مشتريات التاجر والاشتراكات

**الملفات:** `apps/merchant/*`، `supabase/functions/revenuecat-webhook/*`، إعدادات المنتجات والاختبارات والوثائق.

**العمل:** دمج RevenueCat في تطبيق التاجر فقط، عروض وأسعار المتجر المحلية، استعادة الشراء وإدارة الاشتراك، Webhook موثق يستعلم عن الحالة الحالية، وحالات التجديد والإلغاء والانتهاء وفشل الدفع.

**الاعتماديات:** المراحل 2 و5؛ حسابات Apple/Google وRevenueCat ومنتجات Sandbox. الاشتراك لا يبدأ تلقائياً عند انتهاء 30 يوماً.

**معايير القبول:** الخادم وحده يمنح الاستحقاق؛ Webhook مكرر/متأخر/غير موثق لا يفسد الحالة؛ السعر المعروض يأتي من المتجر؛ لا تظهر شاشة شراء للعميل.

### المرحلة 9 — الخصوصية والحذف والاعتمادية

**الملفات:** كلا التطبيقين، وظائف/ترحيلات حذف الحساب، `public/legal/*`، وإعدادات السجل والتعافي.

**العمل:** حذف داخل التطبيق ورابط ويب عام، إخفاء بيانات الهوية وفق قرار قانوني، سياسة احتفاظ ونسخ احتياطية، وضع دون اتصال آمن، وتسجيل أعطال خالٍ من تفاصيل المعاملات.

**الاعتماديات:** مراجعة قانونية عراقية وبيانات الجهة ومزودي الخدمة والاستضافة وفترات الاحتفاظ.

**معايير القبول:** تدفق الحذف لا يمس تاريخ الطرف الآخر؛ لا تُخزن أسرار أو بيانات معاملات في السجلات؛ استعادة نسخة احتياطية مجرّبة؛ سياسة الخصوصية مطابقة للشيفرة.

### المرحلة 10 — تجهيز المتاجر والإطلاق

**الملفات:** ملفات إعداد Expo/EAS، الأيقونات والصور، `docs/STORE_SETUP.md`، `docs/RELEASE_CHECKLIST.md`، ووصف المتاجر.

**العمل:** استبدال معرفات `com.example.*` بعد اعتماد اسم وهوية الشركة، إعداد builds، اختبارات أجهزة iOS/Android، بيانات المتجر والخصوصية والدعم، والتحقق من السعر العراقي.

**الاعتماديات:** جميع المراحل السابقة، حسابات نشر المتاجر، بيانات قانونية حقيقية ومراجعة المحامي.

**معايير القبول:** إغلاق كل عناصر `docs/RELEASE_CHECKLIST.md` واختبار نسخ المتاجر قبل أي إرسال للمراجعة. لا يعلن عن جاهزية النشر قبل ذلك.

## ترتيب التنفيذ الحالي

بناء الواجهات مستمر بتوجيه المستخدم، بينما تبقى المرحلة 1 مفتوحة إلى أن يتوفر Docker-compatible runtime وتنجح ترحيلات Supabase واختبارات RLS. كل تدفق جديد يعتمد على RPC أو مخطط قاعدة البيانات يحتاج مراجعة وتشغيلًا محليًا قبل اعتباره جاهزًا للاستخدام الحقيقي.
